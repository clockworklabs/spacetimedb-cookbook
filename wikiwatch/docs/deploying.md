# Deploying wikiwatch

Run these commands from the `wikiwatch` directory, not from `docs/`. For running wikiwatch locally,
see the [README](../README.md#development).

## The module and the client

```bash
spacetime login
spacetime publish <database name>   # the module, to Maincloud
pnpm build                          # the client, into dist/
```

`spacetime.json` sends `spacetime` commands to Maincloud unless you pass `--server`.

Set `VITE_SPACETIMEDB_HOST` (`wss://maincloud.spacetimedb.com`) and `VITE_SPACETIMEDB_DB_NAME` before
building. The client reads them at build time, not when it runs. Routes live in the URL fragment, so any
static host can serve `dist/` as it is.

When a release changes the module, publish it before deploying the client, so a new client never connects
to an old module.

Publishing doesn't touch the timer tables. When a release changes an interval in
`spacetimedb/src/schedules.ts`, or adds a scheduled process, bring the database's timers in line after
publishing:

```bash
spacetime call --no-config --server maincloud <database name> update_schedulers
```

Without `--no-config`, the CLI takes the database name from its config and reads `<database name>` as the
reducer's name. The call is refused unless your identity is an admin in the database's private `user` table.
`init` adds whoever published the database, but a database created before that table existed has nobody
in it, so add yourself once:

```bash
spacetime sql --no-config --server maincloud <database name> \
  "INSERT INTO user (identity, admin) VALUES (0x$(spacetime login show | awk '{print $NF}'), true)"
```

The Wikipedia contact is stored per database, so a new database needs it set too:

```bash
scripts/set-contact.sh <database name> maincloud
```

## Vercel

Link this directory to a Vercel project once, and give the project the client's build-time settings:

```bash
vercel link --yes --project wikiwatch
vercel env add VITE_SPACETIMEDB_HOST production,preview \
  --value wss://maincloud.spacetimedb.com --no-sensitive --yes
vercel env add VITE_SPACETIMEDB_DB_NAME production,preview \
  --value <database name> --no-sensitive --yes
```

`vercel link` creates the project if it doesn't exist yet. It keeps the link in `.vercel/` and a
development token in `.env.local`, both gitignored. It may also append a bare `.env*` to `.gitignore`,
which you can drop.

Then, for each release, deploy from this directory:

```bash
vercel deploy --prod
```

The CLI uploads the files on disk, uncommitted changes included, rather than what you've pushed, so check
out the commit you mean to release first. Vercel builds the client, and reads the two variables only while
building, so after changing one with `vercel env`, deploy again.

- `vercel deploy` makes a preview deployment and leaves production alone.
- `vercel rollback <deployment url>` points production back at an earlier deployment, which `vercel ls`
  lists.
- `vercel inspect <deployment url> --logs` shows a deployment's build log.

Vercel's Git integration can deploy on every push instead. It needs Vercel's GitHub app installed for the
repository, and the project's root directory set to this one:

```bash
vercel project update --root-directory wikiwatch
```

### pnpm and Node versions

`package.json` pins pnpm with `packageManager`, and Node 24 with `engines`. Vercel reads the pin, and its
build log should say ``Detected `pnpm-lock.yaml` version 9 generated by pnpm@12.x from
package.json#packageManager``. If it says pnpm 10 instead, the build image has no pnpm 12, so set
`ENABLE_EXPERIMENTAL_COREPACK=1` and let Corepack install it. Corepack 0.34 can't run pnpm 12, but the 0.36
in Node 24 can.
